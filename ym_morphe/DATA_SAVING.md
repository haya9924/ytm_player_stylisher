# データ節約の実機確認（YouTube Music 9.30.53）

- **曲の再生を優先** は、準備・バッファリング・シーク中に、対象の次曲先読みだけを一時的に控える既存の機能です。現在の曲、画質・音質、通常の通信を制限しません。
- **前回の再生を少ない通信で再開する** はパッチ適用時の別オプション（初期オフ）です。標準アプリが保存済みキューを一時停止で復元した後、対象分岐の追加キュー取得だけを省きます。並行復元のため先に始まるサーバー取得は止めません。普通に再生したときの通信量や通信料金が減る機能ではありません。

## 検証結果

同一の Actions バンドルから、同じパッケージ名・署名で、再開オプションだけをオン／オフにした 2 つの APK を作成しました。元のインストールは上書きしていません。両方で `dataSavingDiagnostics=true` にし、ログ `YmDataSaving` で標準アプリが追加取得を送った場合と省いた場合を区別できるようにしました。ログには曲名・ID・URL を含めません。

端末でコールドスタート、複数曲への切り替えと一時停止後の復元を試しました。オン版で約 11 秒の位置に一時停止状態で戻りましたが、この試行では追加取得の送信・省略を示すログをどちらの版でも観測できませんでした。既存の先読み制限でも、実際の再生中に対象のイベントは観測できませんでした。端末・アカウント・標準アプリの分岐に依存するため、この結果から **実際の通信量が減ったとは言えません**。一部の再起動では標準プレイヤーがバックグラウンド再生不可を返したため、その試行は通信量の比較から除外しました。

別途、実際にパッチを適用した端末上の DEX に対して、テスト用 instrumentation から制御された先読み要求を渡しました。対象外の曲の要求は緊急状態ではハンドラ呼び出しが 0 回、緊急状態解除後は 1 回となり、分岐と復帰を確認しました。これは人工的な入力による制御フローのテストで、通常再生中の発生頻度や通信バイト削減の証明ではありません。

実際の対象分岐を確認するには、同じ条件で一時停止から復元し、`adb logcat -s YmDataSaving` の `restore follow-up: submitted`（オフ）と `restore follow-up: skipped`（オン）を比較します。これは追加取得の挙動の比較であり、総通信バイト数の比較とは別です。
