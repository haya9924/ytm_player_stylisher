# 再生優先（1.6.0 / 実験的・初期オフ）

YouTube Music の「ym_morphe プレイヤー設定」で「曲の再生を優先（実験的）」をオンにすると有効です。既存のグラデーション設定と同じ画面です。

## 実装した範囲

これは HTTP 全体の帯域予約・優先度制御ではなく、**現在曲が不安定な間、別の曲の新規先読みを開始しない admission 制御**です。Wi-Fi・モバイル双方に適用します。

- プレイヤーの準備・バッファリング・シーク通知を観測し、別曲の新規先読みを最長 15 秒抑制。
- 再生開始が通知されたら、そこから最大 3 秒（元の 15 秒期限も超えない）で解除。
- 同じプレイヤーの連続した準備・バッファリング通知では 15 秒期限を延長しない。
- 一時停止・終了・停止・エラーで、対応するプレイヤーの制限を解除。
- 無効設定・状態不明・期限切れでは元の動作に戻る fail-open。
- 所有者は弱参照。プレイヤーの元処理や例外処理は変更しない。

## 変更した入口と安全条件

9.30.53 の `bbir.a(bbiq, bbil, bbio, boolean)` は、先読み候補を対応する handler に渡し Optional の future を返す入口です。直接呼び出し元は ClientPrefetchController と SabrPrefetchController。どちらも Optional が空の場合は future の処理を行いません。

`bbiq.a.b`（候補の外側の曲インデックス）と `bbil.b`（現在の外側の曲インデックス）が異なる場合だけ、ポリシーを確認します。**同じ曲のネストされたセグメントは通します。** 制限中は host が既に扱っている `Optional.empty()` を返します。

署名・根拠文字列・レジスタ構成が想定と違う APK では適用に失敗する方針です。認証、再生 URL 取得、汎用 HTTP、現在曲のメディア取得処理を直接変更しません。

## 制約・副作用

- 先読みを「後で必ず再開」するキューは追加していません。スキップされた先読みの再試行は元アプリのイベントに依存し、次曲開始時の待ち時間が増える場合があります。
- 既に開始済みの通信や、他の入口を通る先読みは停止しません。
- 画像・歌詞・ホーム・ログの優先順位、通信速度の配分、十分なバッファ秒数の判定は未実装。
- 複数プレイヤーの状態が混在する場合があるため、期限付き・初期オフです。
- 通信量や再生速度の改善は未測定。実機の再生・バックグラウンド・広告・連続スキップ・シーク・ギャップレスへの影響は未確認です。

## 検証

`PlaybackPriorityStateTest` で無効・期限・状態遷移・別所有者・弱参照・時刻異常を検査します。`tests/check_playback_priority.py ORIGINAL_SMALI PATCHED_SMALI` で通知処理が観測命令以外不変、Application の通常終了前に初期化、外側インデックスだけのガード、元の先読みコントローラーが不変であることを検査します。

Android 上での DEX ロード・再生確認には端末が必要です。適用成功や静的検査だけで動作保証とはしません。
